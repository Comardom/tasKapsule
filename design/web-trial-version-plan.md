# 公网试用版与桌面版双形态方案

## 1. 目标

TasKapsule 同时维护两个产品形态：

| 形态 | 用途 | 胶囊数据存储 |
|---|---|---|
| 桌面正式版 | 用户长期使用，持续实现和优化桌面能力 | 现有 Electron + Go + SQLite |
| 公网试用版 | 让访客在线体验产品，引导下载桌面版 | 浏览器 `localStorage` |

两个形态共享同一套 Vue 前端界面、胶囊数据模型和业务交互；只在数据持久化实现和运行入口上区分。

本方案不替换桌面版的 SQLite，也不要求为公网试用版引入用户系统、服务端数据库或用户间交互。

## 2. 产品边界

### 2.1 桌面正式版

桌面正式版保留现有架构：

```text
Electron -> Go HTTP 服务 -> SQLite
```

继续保留和发展：

- 本机 SQLite 持久化，数据库位于 `~/.taskapsule/data/app.db`。
- Electron 的原生窗口、文件选择和文件保存能力。
- Go 后端的 CRUD、分页和未来的业务能力。
- 后续可能实现的本地附件复制、系统通知、闹钟提醒等桌面能力。

桌面版是长期使用的正式产品，SQLite 不应被 `localStorage` 替换。

### 2.2 公网试用版

公网试用版是纯静态 Web 应用：

```text
浏览器 -> localStorage
```

其服务端只分发 HTML、JavaScript、CSS 和静态资源，不接收、不保存、不读取访客的胶囊内容。

公网试用版的规则：

- 不注册、不登录。
- 不建立服务端用户档案。
- 不建立公开内容、评论、分享或其他访客间交互。
- 每位访客的胶囊仅保存在其当前浏览器和当前站点域名的 `localStorage` 中。
- 清除站点数据、使用无痕窗口、切换浏览器或更换设备后，数据可能丢失。
- 用户可以通过 JSON 导出功能自行备份数据。
- 用户可将 JSON 导入桌面正式版，完成从试用到正式使用的迁移。

## 3. 总体架构

```text
                         共用 Vue 前端
      日历 / 胶囊 / 时间线 / 主题 / 字体 / 导入导出
                               |
                        统一 Capsule API
                         /              \
             桌面版存储实现              Web 试用版存储实现
        Axios -> Go REST -> SQLite       localStorage
```

上层 Vue 组件和 Pinia store 统一调用 `capsuleApi`，不直接依赖 SQLite、Axios 或 `localStorage`。

现有的调用方式应保持一致：

```ts
capsuleApi.getAll()
capsuleApi.getAllPaginated(page, perPage)
capsuleApi.create(data)
capsuleApi.update(id, data)
capsuleApi.delete(id)
capsuleApi.deleteAll()
```

桌面版和 Web 版分别提供这些操作的实现。这样，新建、编辑、删除、日历时间线和导入导出等页面不必维护两份业务逻辑。

## 4. 前端代码组织

建议将当前 API 层按职责拆分为：

```text
frontend/src/utils/
  capsuleApi.ts              # 对上层导出统一 capsuleApi
  capsuleApiDesktop.ts       # Axios -> Go REST API -> SQLite
  capsuleApiWeb.ts           # localStorage CRUD
  capsuleStorage.ts          # Web 存储格式、读取、校验、迁移、演示数据
```

职责说明：

| 文件 | 职责 |
|---|---|
| `capsuleApi.ts` | 根据构建目标选择桌面或 Web 实现，并向组件导出统一接口。 |
| `capsuleApiDesktop.ts` | 承接现有 Axios 调用，继续访问 Go 后端。 |
| `capsuleApiWeb.ts` | 在浏览器中完成胶囊的读取、新建、更新、删除和分页切片。 |
| `capsuleStorage.ts` | 管理 `localStorage` key、数据版本、容错解析、ID 分配和演示数据。 |

## 5. 构建目标

通过构建变量显式区分运行形态：

```text
VITE_APP_TARGET=desktop
VITE_APP_TARGET=web
```

规则：

| 构建目标 | 存储实现 | 后端健康检查 |
|---|---|---|
| `desktop` | `capsuleApiDesktop` | 保留，等待 Go 服务就绪。 |
| `web` | `capsuleApiWeb` | 跳过，应用直接进入主界面。 |

不应通过是否存在 Electron API、页面 URL 或端口来猜测运行模式。显式构建变量能避免 Web 试用版错误请求 `localhost:9999`，也避免桌面版意外使用浏览器存储。

建议提供独立构建命令：

```text
pnpm build:desktop
pnpm build:web
```

Web 构建产物应使用独立目录，例如：

```text
frontend/dist-web/
```

避免与桌面版 Electron 打包使用的 `frontend/dist/` 混用。

## 6. Web 版数据设计

Web 试用版使用一个专用 `localStorage` key：

```text
taskapsule.web.capsules.v1
```

不直接裸存胶囊数组，而是保存可升级的对象：

```json
{
  "version": 1,
  "nextId": 8,
  "updatedAt": "2026-09-10T12:00:00.000Z",
  "capsules": []
}
```

字段含义：

| 字段 | 说明 |
|---|---|
| `version` | 存储结构版本，用于后续字段升级和迁移。 |
| `nextId` | 下一个数值 ID，避免删除后复用 ID。 |
| `updatedAt` | 最后保存时间，可用于备份提示或故障排查。 |
| `capsules` | 胶囊数组，字段与当前桌面版 `Capsule` 模型保持一致。 |

读取时必须处理以下异常：

- key 不存在：创建初始数据或演示数据。
- JSON 损坏：不让应用崩溃，提示用户并提供恢复演示数据的操作。
- 数据版本不支持：保留原始备份后做迁移或降级处理。
- `localStorage` 写入失败或空间不足：提示用户导出 JSON 并清理数据。

## 7. 公网试用体验

### 7.1 首次进入

首次访问 Web 试用版时，建议自动写入一组精心设计的演示胶囊，至少包括：

- 一条普通笔记。
- 一条紧急任务。
- 一条无日程的灵感。
- 一条跨多天的日程。
- 一条带截止时间的任务。
- 一条已完成日程。

演示数据应覆盖单列列表、双列时间线、日历跳转、分类颜色和详情展开等关键体验，避免访客进入空白页面后无法理解产品能力。

### 7.2 访客能力

试用版应允许访客：

- 查看和编辑演示数据。
- 新建、编辑、删除胶囊。
- 切换日历、单双列视图、日程显示模式、主题和字体。
- 导入 JSON。
- 导出 JSON。
- 清空本地试用数据。
- 恢复演示数据。

“恢复演示数据”和“清空本地试用数据”都应先要求用户确认，防止误覆盖自己的临时记录。

### 7.3 隐私和数据提示

首次使用、导入导出区域或下载入口附近应展示：

> 试用数据仅保存在当前浏览器，不会上传到服务器。清除站点数据、使用无痕窗口、更换浏览器或设备后，数据可能丢失。如需长期保存，请导出 JSON 或下载桌面版。

这既是用户体验提示，也是公网试用版的数据边界说明。

## 8. 桌面版与 Web 版的数据迁移

JSON 是两个形态之间的迁移格式，必须保证：

```text
Web 试用版导出 JSON -> 桌面版可导入
桌面版导出 JSON -> Web 试用版可导入
```

要求：

- 两端使用相同的 `Capsule` 字段名称和枚举值。
- 导入时保留日程、分类、附件路径、闹钟和图标等已支持字段。
- 为导出格式增加版本字段，便于未来兼容。
- 导入时校验 `classification`、`scheduleStatus`、`isWithSchedule` 和必要字段。
- 导入失败应逐条报告，而不应让整个应用失去可用性。

当前导入逻辑会在导入前剔除 `scheduleIcon` 字段；在双形态上线前需要修复，确保导入导出不会丢失已有数据。

## 9. 功能边界

| 能力 | 公网试用版 | 桌面正式版 |
|---|---|---|
| 创建、编辑、删除胶囊 | 支持 | 支持 |
| 日历、时间线、主题、字体 | 支持 | 支持 |
| JSON 导入导出 | 支持 | 支持 |
| 服务端保存用户胶囊 | 不支持 | 不支持 |
| 长期可靠持久化 | 不保证 | SQLite 支持 |
| 本地文件附件 | 不主推，不承诺上传能力 | 后续实现 |
| 系统通知和闹钟提醒 | 不支持 | 后续实现 |
| 用户系统和跨设备同步 | 不支持 | 当前不支持 |
| 访客间公开交互 | 不支持 | 不支持 |

Web 试用版的 `audioPath`、`attachmentPaths` 等字段可先保留为展示信息，但不应宣传为真正的上传能力。真正的本地文件管理应作为桌面版后续能力。

## 10. 响应式要求

当前主界面主要按桌面横向布局设计。公网试用版需要至少支持窄屏访问：

- 宽屏：保持当前日历和胶囊区横向布局。
- 窄屏：日历置于上方，胶囊列表置于下方。
- 窄屏默认使用单列视图。
- 双列时间线在窄屏可改为上下区域或 Tab 切换。
- gate-gap 的隐藏菜单需要有可触达的窄屏替代入口。
- 新建、编辑、导入导出弹窗宽度不得超出视口。
- 下载桌面版入口必须在手机浏览器中清晰可见。

目标不是把项目改造成移动端 App，而是保证访客通过手机访问试用链接时能够完成核心体验。

## 11. 部署方案

Web 试用版是静态站点，无需后端 API、数据库、容器或账号系统。

可选静态托管平台：

1. Cloudflare Pages。
2. GitHub Pages。
3. Netlify。
4. Vercel。

现有前端使用 Hash 路由，适合静态托管，不需要额外配置服务端 SPA 路由重写。

公网页面除试用应用外，应提供：

- “下载桌面版”入口。
- Linux 和 Windows 安装包链接。
- 项目功能简介。
- 本地存储和隐私说明。
- JSON 导出后可导入桌面版的迁移指引。
- GitHub 仓库、更新日志或问题反馈链接。

## 12. 实施顺序

### 阶段一：抽象存储接口

- 将现有 Axios + Go REST 调用迁入 `capsuleApiDesktop.ts`。
- 建立统一 `capsuleApi` 类型和入口。
- 确保桌面版行为与当前版本一致。

### 阶段二：实现 Web 本地存储

- 实现 `capsuleApiWeb.ts` 的 CRUD。
- 实现 `capsuleStorage.ts` 的版本化读写和容错。
- 实现 `localStorage` 数据的 ID 管理。
- 增加默认演示数据、恢复演示数据和清空数据操作。

### 阶段三：建立双构建和启动逻辑

- 增加 `desktop`、`web` 两种构建变量和构建命令。
- Web 版跳过 Go 后端健康检查，直接进入应用。
- Web 构建产物使用独立目录。

### 阶段四：保证数据可迁移

- 修复导入导出字段丢失问题。
- 统一两端导入导出格式。
- 增加导入格式校验和版本处理。

### 阶段五：完成试用版体验和部署

- 增加隐私提示、数据丢失提示和桌面版下载入口。
- 完成窄屏布局的核心可用性适配。
- 部署静态 Web 构建产物到公网平台。

## 13. 结论

推荐采用“同仓库、同前端、双存储实现、双构建目标”的方案：

```text
桌面正式版：Electron + Go + SQLite
公网试用版：静态 Web + localStorage
```

该方案满足以下要求：

- 原有桌面软件继续按现有架构推进。
- 公网访客可直接试用核心功能。
- 不需要用户系统。
- 不保存访客胶囊到服务器。
- 不存在公开交互或访客间数据可见性。
- Web 版可通过 JSON 导出迁移到桌面正式版。
- 后续若 Web 版数据量或功能需要增长，可在不改上层 Vue 组件的前提下，将 `capsuleApiWeb` 从 `localStorage` 升级为 IndexedDB。
